Last time, I promised you kubelet. I said understanding it would get you `pods` (Kubernetes's process model), `nodes` (its hardware abstraction), and volumes (its storage abstraction) for free, because kubelet is the one controller that reconciles all three. That's still true. But before we get into any of that, it's worth pausing on why kubelet, of all the controllers in this system, is the right place to actually start digging in one at a time.

## The controller that isn't like the others

Every controller you met in the last article followed the same shape: watch a resource, compare spec to status, write the difference back to kube-apiserver. Kubelet does that too -- it watches `Pod` objects scheduled to its own node, and reconciles what's actually running against what the spec says should be running. Same pattern, no exceptions.

But kubelet is also the one controller that breaks the mold in almost every other way:

- **Every other controller we looked at writes its decisions to etcd and stops.** Kubelet has to go further -- it has to make something real happen on a physical (or virtual) machine. It doesn't just PATCH a status field and call it done; it talks to an actual container runtime over CRI (the Container Runtime Interface) to pull images, start and stop real OS processes, and mount real storage. Every other controller's "reconcile" ends at kube-apiserver. Kubelet's begins there.
- **Every other controller we looked at runs a handful of replicas, tucked away on control-plane nodes.** Kubelet runs on _every single node in the cluster_, control-plane nodes included. There isn't a "kubelet controller" sitting off in `kube-controller-manager` somewhere watching all pods cluster-wide -- there are as many independent kubelets as you have machines, each one scoped to just its own node's slice of the world.
- **And strangest of all: in a self-hosted cluster, kubelet has to bootstrap the very control plane it depends on.** kube-apiserver, kube-controller-manager, kube-scheduler, and etcd are typically deployed as _static pods_ -- manifest files sitting on disk that the local kubelet reads and starts directly, without needing a running kube-apiserver to schedule them, because obviously kube-apiserver can't schedule its own first instance through the normal Pod-scheduling path. Chicken, meet egg. On that kind of cluster, kubelet isn't a peer of kube-controller-manager -- it's the thing keeping kube-controller-manager's container alive in the first place.

That last one is worth sitting with for a second, because it's the cleanest possible rebuttal to anyone still clinging to the idea that "Kubernetes" is a single coordinated thing with some central boot sequence. The truth is messier and more interesting: an ordinary node-level agent, running the exact same watch-and-reconcile loop as anything else in this system, quietly holding up everything else by reading YAML off a disk.

## Static pods, or: does kubelet have its own API server?

That's a fair question to ask, and the official docs kind of invite it. Here's how they describe a static pod: _"specialized Kubernetes pods managed directly by a specific node's kubelet daemon rather than the central API server."_ Read that quickly and you'll come away thinking kubelet must be running some parallel control plane of its own -- a second API, rivaling kube-apiserver, just for this one weird class of pod.

It isn't. What kubelet actually does is dumber than that, in the best way.

Kubelet is configured with one of two sources for static pods: `staticPodPath`, a local directory it periodically re-scans for manifest files, or `staticPodURL`, a URL it periodically polls with a plain `GET`. (Older clusters do this with the equivalent, now-deprecated flags, `--pod-manifest-path` and `--manifest-url`.) Notice the shape of both of these: kubelet is _pulling_. There's no listener socket, no accepted connections, no auth handshake where some other client pushes a Pod spec at it. It isn't serving anything here. It's just periodically looking at a file, the same way `tail -f` looks at a file, and doing something about it when the contents change.

So "rather than the central API server" doesn't mean "kubelet has its own API server instead." It means "the desired state for this one specific pod doesn't live in etcd, it lives in a file, and kubelet is watching the file the same way it'd otherwise watch kube-apiserver." Same reconcile loop on the inside, completely different, much dumber source feeding it.

Once kube-apiserver actually exists -- which, on a self-hosted control-plane node, it will, because it's one of the static pods this exact mechanism just started -- kubelet does one more thing: it creates a **mirror pod**, a read-only copy of the static pod's identity in kube-apiserver, purely so `kubectl get pods` can see it, so you can read its logs, so label selectors work on it like anything else. But it's one-way and it's decorative. `kubectl delete` on that mirror pod does nothing; the docs' own example shows it: you delete it, kubectl says `pod "static-web-my-node1" deleted`, and the pod is still sitting there running, because the thing you deleted was never the source of truth. The only way to actually change or remove a static pod is to edit or delete the file on disk and let kubelet notice on its next pass.

There's one more restriction worth knowing, because it's not an accident: **a static pod's spec cannot reference a `ConfigMap`, `Secret`, or `ServiceAccount`.** At first that sounds like an arbitrary limitation. It isn't -- it's what keeps the whole trick airtight. If a static pod's spec could point at a Secret, kubelet would have to ask kube-apiserver to resolve it, and kube-apiserver might be the very static pod you're trying to start in the first place. Forbidding the reference entirely means kubelet can always fully reconcile a static pod using nothing but the file in front of it and the local container runtime, whether kube-apiserver has ever existed on this machine or not.

Which gets at something worth sitting with even more than the bootstrap trick itself: **this whole article, and most of the last one, is built on a recursive pattern.** A controller watches a resource. That resource was written by another controller, which was watching a resource written by yet another controller, all the way up and down through kube-apiserver and etcd. It's controllers watching resources, watching resources, watching resources -- turtles all the way down, near enough.

Except it isn't, quite. Static pods are the one place that recursion actually hits a floor, and the floor isn't Kubernetes-shaped at all. It's a plain file, on a local disk, with no `resourceVersion`, no watch, no RBAC, not an API object of any kind. Somewhere underneath every turtle, there's one that's just a filesystem. That's not a flaw in the design -- it's the one non-negotiable exit ramp the entire system needs in order to bootstrap itself into existing in the first place.

## Outline

Rough shape for the rest of this piece, subject to change as we go:

1. **What kubelet actually watches** -- `GET /api/v1/pods?fieldSelector=spec.nodeName=<node>&watch=true`, same watch mechanism from part 1, just scoped to one node instead of the whole cluster.
2. **The SyncLoop** -- kubelet's own internal reconcile loop for pods. What "spec vs. status" actually means at this layer (desired containers vs. running containers), and how that maps back to the `status.containerStatuses` field we saw in the watch-event examples in part 1.
3. **CRI: where the YAML stops and the OS starts** -- the Container Runtime Interface boundary. This is the point where a `Pod` object's `spec.containers[].image` stops being a string in etcd and becomes an actual `containerd`/CRI-O call. Worth a real example: trace one container spec from PodSpec through to a running process.
4. **Kubelet's other internal loops** -- it's not just the SyncLoop. Status manager (writes `status` back to kube-apiserver), volume manager (mounts/unmounts storage -- this is where "volumes" pays off), image and container garbage collection, and the probe manager (liveness/readiness/startup checks -- ties back to why a pod flips to `CrashLoopBackoff`, which we handwaved all the way back in part 1's intro).
5. **Nodes: kubelet talking about itself** -- the heartbeat mechanism (`Lease` objects, `coordination.k8s.io/v1`), and how kubelet PATCHes its own `Node` object's `status.conditions` (`MemoryPressure`, `DiskPressure`, `PIDPressure`, `Ready`). Good spot to reintroduce the Node Lifecycle Controller from `kube-controller-manager` as the other half of this conversation -- kubelet reports, a totally separate controller decides what to do about silence.
6. **Static pods and the bootstrap paradox** -- ~~drafted above~~. Still need: a real worked example (probably `kube-apiserver`'s own static pod manifest from a kubeadm cluster), and the explicit contrast with managed control planes (GKE/EKS/AKS), where this whole layer is invisible to the user because the cloud provider runs it on infrastructure you never see.
7. **Landing the plane** -- tie it back to the thesis from part 1: kubelet is proof the pattern doesn't change even at the edges of the system. It just happens to be the controller with the most interesting edges.
