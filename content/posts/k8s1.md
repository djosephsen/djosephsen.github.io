## There is no "Kubernetes"
We are invited to think of kubernetes as a bulbous sort of centralized orchestration monolith. **Kubernetes** is the thing that scales stuff up and down, **kubernetes** deploys things, **kubernetes** handles RBAC etc... Perhaps we've heard of a "controller" or two -- the pod controller, the deployment controller, but **kubernetes** runs them. Right? I mean, heck the name Kubernetes even refers to a ship captain... or something... right? A single person? Steering a ship? That's gotta be a monolith. Right?

**Lies** my friend. There is no monolithic entity in the system that you can point at which is called Kubernetes. There is no kubernetes process nor binary. There is no controller-controller -- no captain is steering this ship. In point of fact, _Kubernetes_ is just a proper noun we've assigned to a strangely shaped microservices architecture. A distributed system where every microservice is wired to a _single, centralized API endpoint_.

## Meet kube-apiserver
This endpoint is called "kube-apiserver", and there's absolutely nothing magic about it. I say that, because given the involvement of Go and containers and cloud-nativity in general, you might assume some binary protocols are involved. Webassembly, GRPC, Protobuf, fancy magic-pants stuff like that. 

Nope. Kube-apiserver speaks HTTP GET and POST, which means _every service_ in kubernetes speaks plain ole HTTP GET and POST.

Ok that's fine for _this interface_, but what about all the other kubernetes interfaces?

_There aren't any other interfaces._ There is **one** interface, it is kube-apiserver, and it speaks HTTP GET and POST. This singular interface is used by Humans to do things like get pod status, by machines to do things like deploy new workloads, and even by the internal kubernetes services to do things like change the state of a pod from `Ready` to `CrashLoopBackoff`. **All operations use one interface: kube-apiserver**

_Well that's obvious bullcrap Dave_ I can hear you say. _What about Apply, Patch, and Update? There are more operations than get and post._

The operations we talk about like those performed by commands like `kubectl apply` are details encapsulated in the body of an HTTP Post and sent to kube-apiserver by kubectl. Lets take a look at one.

```
post body
```

Every kubectl command you run against a cluster creates either an HTTP GET or POST request like this one from your personal computer to the kube-apiserver endpoint described by your current kubernetes context. That's all that's happening. Kubectl says _What's the url of your kubernetes cluster's kube-api endpoint?_ and then it sends an HTTP GET or POST to it.

Lets look at what happens when we `kubectl get pods`

```

```

When you call `kubectl get pods` for example, a GET request like the one above is created by kubectl and sent to the kube-apiserver endpoint. Kube-apiserver responds with a list of pods, which kubectl reformats and parrots back out to you.

_Well that's obvious bullcrap Dave_ I can hear you say. _I can kubectl get logs and  return a stream of log messages in my terminal. And everyone knows http get can't encompass streaming-logs functionality_

Sure it can. When you call `kubectl get logs` kube-apiserver upgrades the connection to chunked streaming mode, like any other streaming service. It then interacts with the kubelet(s) running on the pod(s) you want logs from and proxies back the logs to kubectl, which parrots them back to you. You're never talking to anything but kube-api server, and you're never speaking any protocol but http/get.

_Well that's obvious bullcrap Dave_ I can hear you say. _I can kubectl exec to a pod and http get can't encompass full terminal functionality_

Of course it can. When you call `kubectl exec` kube-apiserver merely upgrades the connection to a bidirectional web-socket, interacts with the kubelet on the pod to derive a shell, and then cross-wires stdin, stdout, and stderr accordingly. You're never talking to anything but kube-api server, and you're never speaking any protocol but http/get.

## There is only one interface. There is only one protocol.
Kube-apiserver is the one and only interface into the distributed system we describe as "kubernetes" and kubeapiserver only speaks HTTP GET and POST. That's weird I grant you, but it also simplifies quite a bit. It means, for example, that **all role-based access control lives in one place: kube-apiserver**.  

Because literally **anything** in the system that wants to interact in any way with **any other** component of the system, does so by traversing kube-apiserver, this shared endpoint handily becomes the single point of authorization in the system. All RBAC is implemented on http get and post requests to kube-apiserver. Easy peasy. 

Hey check that out! Now you have a high-level mental model for how kubernetes role-based access control works, and lemme tell ya, _NOBODY has a mental model of the architecture of kubernetes role-based access control_. You're already killing it.
