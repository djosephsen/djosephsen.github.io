## There is no "Kubernetes"
We are invited to think of kubernetes as a bulbous sort of centralized orchestration monolith. Kubernetes scales things up and down, kubernetes deploys things, kubernetes handles RBAC etc... Perhaps we've heard of a "controller" or two -- the pod controller, the deployment controller, but kubernetes runs them. Heck the name Kubernetes even refers to a ship captain... or something... right? A single person? steering a ship? Right?

Lies. There is no monolithic entity in the system that you can point at which is called Kubernetes. There is no kubernetes binary. Kubernetes is actually just the name of a very strangely shaped microservices architecture where every service shares a single API endpoint. 

## Meet kube-apiserver
This endpoint is called "kube-apiserver", and there's absolutely nothing magic about it. I say that, because given the involvement of Go and cloud-nativity, you might assume the presence of binary protocols, GRPC, Protobuf, fancy magic-pants malarky. Nope. Kube-apiserver speaks HTTP GET and POST. 

Ok that's fine for this interface, but what about all the other kubernetes interfaces.

_There aren't any other interfaces._ There is one interface, it is kube-apiserver, and it speaks HTTP GET and POST. This singular interface is used by Humans to do things like get pod status, by machines to do things like deploy new workloads, and even by the internal kubernetes services to do things like change the state of a pod to `CrashLoopBackoff`. **All operations use one interface: kube-apiserver**

_Well that's obvious bullcrap Dave_ I can hear you say. _What about Apply, Patch, and Update?_

The operations we talk about like `kubectl apply` are encapsulated in the body of an HTTP Post and sent to kube-apiserver by kubectl. Lets take a look at one.
```
post body
```
When you call `kubectl get pods` an analogous GET request is created by kubectl and sent to the kube-apiserver endpoint, resulting in a list of pods kubectl parrots back out to you.

_Well that's obvious bullcrap Dave_ I can hear you say. _I can kubectl get logs and http get can't encompass streaming-logs functionality_

Sure it can. When you call `kubectl get logs` kube-apiserver merely upgrades the connection to chunked streaming mode, like any other streaming service. It then interacts with the kubelet(s) running on the pod(s) you want logs from and proxies back the logs to kubectl, which parrots them back to you. You're never talking to anything but kube-api server, and you're never speaking any protocol but http/get.

_Well that's obvious bullcrap Dave_ I can hear you say. _I can kubectl exec to a pod and http get can't encompass full terminal functionality_

Of course it can. When you call `kubectl exec` kube-apiserver merely upgrades the connection to a bidirectional web-socket, interacts with the kubelet on the pod to derive a shell, and then cross-wires stdin, stdout, and stderr accordingly. You're never talking to anything but kube-api server, and you're never speaking any protocol but http/get.

## There is only one interface. There is only one protocol.
My point here (in case you missed it) is that kube-apiserver is the one and only interface into the distributed system we describe as "kubernetes" and kubeapiserver only speaks HTTP GET and POST. This is a comforting thought, because among other things, it means **all role-based access control lives in kube-apiserver**.  

Because literally **anything** in the system that wishes to interact in any way with any other component of the system does so through kube-apiserver, it becomes a single point of authorization in the system. Easy peasy. Hey, you understand how kubernetes role-based access control works now, and literally NOBODY understands how kubernetes role-based access control works. You're already killing it.
